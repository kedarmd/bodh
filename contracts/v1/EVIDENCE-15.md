# Issue #15 discussion acquisition evidence

`inspect --kind discussions` performs read-only GitHub acquisition from the stored preparation identity. It paginates the GraphQL review-thread connection first, then every acquired thread's nested comments connection independently. Afterward it paginates the REST pull-request review-comments connection to enrich exact original path/side/range metadata that GraphQL does not expose. Every acquired GraphQL and REST page is committed in its own short SQLite transaction before the next request; later transport, permission, timeout, malformed-cursor, repeated-cursor, duplicate/null-node, count-change, size-limit, missing-join, or inconsistent-join failures preserve earlier pages and identify the affected connection and cause.

The additive SQLite schema uses its own `discussion_schema_migrations` version table (version 1) alongside the preparation database's existing `PRAGMA user_version=1`. This lets discussions upgrade an existing issue #13 database without rewriting the preparation schema version. Page rows reference the preparation and observation with foreign keys; WAL is enabled. Acquisition never runs while a database write transaction is open. Restart tests reopen the original preparation and the complete/partial discussion observations.

The compact prepare/manifest summaries expose expected/fetched thread and comment counts, availability, completeness, the first affected connection/cause, count-change status, original-side enrichment availability, and `moving_non_atomic` consistency. Unknown GraphQL totals remain `null`. Inspection retains each thread's GraphQL node ID, comment/reply GraphQL IDs, full decimal database IDs, `replyTo` relationships, author/association, body/timestamps, current path and ranges, current/original line ranges, resolution/outdated state, and viewer permissions. Matching REST review-comment data is preserved under `rest_location` for each comment and its root thread, including current/original paths, sides and ranges, associated review/comment IDs, commit IDs and author metadata. The join is by `fullDatabaseId`; reply identity, author/association and overlapping GraphQL/REST path/range values are checked for consistency. Missing or inconsistent IDs are not guessed: they make the exact REST or per-thread REST connection incomplete. The combined observation remains `moving_non_atomic`; GraphQL and REST reads are not represented as an atomic server snapshot.

Controlled `gh` fixtures cover multiple outer, nested and REST pages, an empty discussion with unknown total, restart and preparation-schema migration, comments and thread metadata, GraphQL partial permission errors, HTTP permission loss, nested timeout, repeated outer and nested cursors, duplicate and null nodes, moving counts, successful ID joins, missing/duplicate/mismatched REST records, and a later REST-page permission failure preserving the earlier page. The REST fixtures accept only an explicit `--method GET` and fail when that option is absent. This guards against `gh api` defaulting to POST when form fields are supplied. Aggregate acquisition is bounded to 8 MiB of responses, at most 100 rows per page, and explicit row/page limits. No live account call or review/thread/comment mutation was performed.

An independent Standards review found that the original REST command supplied `-F` fields without `--method GET`, which makes `gh api` default to POST. The request now explicitly sets GET, and the GET-only controlled fixture reproduced the missing-method failure before the correction and passed afterward.

`CARGO_BUILD_JOBS=2 CARGO_TARGET_DIR=/home/kedarmd/dev/bodh/target cargo test --locked --test discussions -- --nocapture` passed all 15 discussion acquisition tests. `CARGO_BUILD_JOBS=2 CARGO_TARGET_DIR=/home/kedarmd/dev/bodh/target ./scripts/validate desktop` passed; full runner output is preserved in [VALIDATE-15-final.log](VALIDATE-15-final.log). No GUI trial applies to this headless acquisition slice.


## Deadline fixture stabilization — 2026-11-07

The controlled nested-page timeout fixture used a 100 ms total operation deadline, which also covered process startup and first-page acquisition. It failed intermittently even though its delayed page was deliberately held for 3 seconds. Ten isolated baseline runs produced 6 passes and 4 failures, with failures observing no durable first-page comment. Increasing only the fixture deadline to 1 second (still 2 seconds shorter than the controlled delayed response) produced 10/10 focused passes and 15/15 passes in the complete discussion integration suite. The repeated-run results are recorded in [AC15-DISCUSSION-TIMEOUT-CALIBRATION-2026-11-07.log](AC15-DISCUSSION-TIMEOUT-CALIBRATION-2026-11-07.log); the final complete desktop run is [VALIDATE-39-SPACING-FINAL-2026-11-07.log](VALIDATE-39-SPACING-FINAL-2026-11-07.log). This changes test calibration only; the production timeout behavior is unchanged.
